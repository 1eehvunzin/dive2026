## 0. 한 줄 결론

이 제품은 **선정 알고리즘이 아니다.**  
KODATA·부산TP 원장에서 **서류에 안 보이는 재무·생존·중복수혜 신호**를 꺼내, 담당자가 30초 안에 “어디를 더 볼지” 정하게 하는 **개별기업 점검 엔진**이다.

분석으로 확정한 핵심:

1. 담당자 선정은 관측 재무 지표로 거의 예측되지 않는다 (AUC ≈ 0.51~0.59).
2. 그런데 **폐업은 일부 지표로 예측된다** (매출 규모 AUC 0.704, 업력 0.671, 고용 0.609).
3. 부채비율·영업적자·매출성장률은 폐업 예측 가중치를 거의 못 쓰거나 0이다 → **참고지표**.
4. 지원 이력은 **episode(선정 단위)** 와 **component(세부 금액·품목)** 를 분리해야 중복수혜 점검이 된다.
5. 탈락·포기 건을 수혜로 세면 신호가 왜곡된다 → **지원대상만** 집계.
6. 자본총계가 거의 0인 기업은 부채비율이 수만 %로 튀므로 **숫자 그대로 쓰지 말고 자본 소진으로 해석**한다.

## 3. 파생지표 산식 (분석 → ETL → 엔진)

### 3.1 ETL (`etl/build_gold.py`)에서 계산

단위: 재무 원천은 **천원**. 화면 표시는 주로 **백만원** (÷1000).

| metric_code | 산식 | unit |
|---|---|---|
| `revenue_level` | 매출액 (raw) | thousand_won → 표시 시 백만원 |
| `employment_level` | 국민연금 가입자 (없으면 종업원) | persons |
| `revenue_growth` | \((rev_t - rev_{t-1}) / rev_{t-1} × 100\) | % |
| `debt_ratio` | \(liabilities / equity × 100\) (equity>0) | % |
| `operating_margin` | \(op_profit / revenue × 100\) 또는 yearly `op_margin_pct` | % |
| `rd_intensity` | \(rd_expense / revenue × 100\) | % |

`equity ≤ 0` 이면 debt_ratio status = `negative_equity`, value = null 가능.

### 3.2 동종 백분위

- 1순위: KSIC 3자리 × 기업규모 (`ksic3_size`)
- 표본 부족 시 KSIC 3 → KSIC 1×규모 → … 폴백
- 화면: `61백분위 · ksic3_size n=125` 형태
- **예측값이 아니라 해석 도구** (v3.3)

### 3.3 임계값 (`server/config/threshold.json`)

코드 하드코딩 금지 원칙. 런타임은 이 JSON을 읽는다.

```json
{
  "survival": {
    "revenue_pctl_caution": 30,
    "tenure_caution_years": 3,
    "employment_pctl_caution": 30,
    "min_employees_viable": 2
  },
  "financial": {
    "debt_ratio_warning": 200,
    "debt_ratio_caution": 100,
    "op_margin_caution_pct": 0
  },
  "support_history": {
    "repeat_episode_caution": 5,
    "consecutive_years_caution": 3,
    "overlap_days_threshold": 30
  }
}
```

의미:

- 매출/고용이 동종 **하위 30백분위 미만** → 주의
- 업력 **3년 미만** → 주의
- 부채비율 **100% 초과 주의, 200% 초과 경고**
- 영업이익률 **0% 미만** → 주의
- 수행기간 교집합 **≥30일** → 중첩 쌍
- 지원대상 episode **≥5** 또는 연속 3년 → 지원 집중 주의

## 4. 지원(BTP) 분석 로직 — 중복수혜의 핵심

### 4.1 episode vs component

```text
episode_id ≈ (기업일련번호, 사업코드, 선정일)
component  = episode 안의 지원구분/품목/금액 행
```

- **횟수(중복수혜 건수)** = episode 수  
- **금액** = component 정제금액 합 (episode `total_amount`)

### 4.2 지원대상 필터 (분석 반영 포인트)

**문제 발견**

- 기존 엔진이 탈락·포기 episode를 수혜 건수에 포함.
- 기업 2124: 원장 5건 중 탈락 2건 → “5건 수혜”처럼 보임.

**해결**

```text
is_awarded = result ∈ {지원대상, *지원대상*, 선정}
```

| 집계 필드 | 의미 |
|---|---|
| `total_episodes` | 원장 전체 (탈락 포함) |
| `awarded_episodes` | 지원대상만 |
| `rejected_or_withdrawn` | 탈락·포기 |
| `recent_3yr_awarded` | 최근 3년 지원대상 |
| `awarded_amount_million` | 지원대상 금액 합 (백만원) |

**목록 API도 동일** (`companies.ts` SQL에 지원대상 조건).

### 4.3 기간 중첩

- 두 지원대상 episode의 `start_date`~`end_date` 교집합 일수
- threshold ≥ 30일만 `overlap_pairs`에 기록
- 날짜 없으면 **0일로 취급하지 않음** (중첩 산출 제외)
- 목적 관계: `same | similar | different | unknown`

### 4.4 동일 목적 정규화

component `support_type` 우선, 없으면 episode `biz_type`.

| 원천 예 | 정규화 목적 |
|---|---|
| 시제품제작, 제품고급화 | 시제품 |
| 인력양성(역량개발지원), 일자리창출or인력양성 | 인력양성 / 고용 |
| 마케팅, 수출지원, 전시회 | 마케팅/수출 |
| 공동기술개발, 기술지도, 기술지원, RnD | 기술/R&D |
| 인증지원 | 인증 |
| 특허지원 | 지식재산 |

지원대상 중 동일 정규화 목적 ≥2 → `same_purpose_repeats`.

### 4.5 금액 품질

| amount_flag | 의미 | 화면 |
|---|---|---|
| ok | 금액 확인 | 정상 표시 |
| missing | null | 금액 미상 |
| zero | 0원 | 원천값 0원 · 의미 확인 |

### 4.6 지원 후 관찰 변화

각 **지원대상** episode에 대해:

- pre = 선정연도 − 1 재무/고용  
- post = 선정연도 재무/고용  
- 매출 변화율, 고용 증감, 신규 특허(누적 등록 차분)  
- 상태: `improved | partial | unchanged | insufficient | overlapped`

**인과 효과로 해석하지 않음.** 중첩 episode는 `overlapped`.

## 5. 재무 함정: 부채비율 98,077% 문제

### 5.1 현상 (기업 2124, FY2024)

| 항목 | 값 (천원) |
|---|---:|
| 매출 | 1,110,436 → **11.1억원** |
| 영업이익 | −914,296 → 이익률 **−82.3%** |
| 부채총계 | 3,391,486 |
| 자본총계 | **3,458** → **3.5백만원** |
| 부채비율 산출 | 3,391,486 / 3,458 × 100 = **98,076.5%** |

산식은 맞다. 그런데 담당자 UI에 “부채비율 98077%”만 띄우면:

- 한은 업종 평균(약 77%)과 갭이 10만 %p처럼 보여 **해석이 불가능**하고
- 실제 메시지는 **자본이 거의 소진됐다**는 것.

### 5.2 분석 규칙 → 코드 (`interpretDebtRatio`)

```text
if equity ≤ 0:
  → "자본총계 0 이하(자본잠식)"
else if equity < 50백만원 OR equity/assets < 5% OR debt_ratio ≥ 1000%:
  → "자본 소진 임박 · 자본총계 X · 산출 부채비율 Y%"
  → nearZeroEquity = true, severe = true
else:
  → "부채비율 Y%"
```

- 원 수치(`value`)는 테스트 정합을 위해 유지.
- 화면/6칸/목록 risk는 **해석 문장** 사용.
- 사업수행 기반: 인력·R&D가 있어도 자본 소진이면 **「충분」이 아니라 「보완 필요」**.

## 6. 30초 점검 칸 (Six-box) — 분석 매핑

구현: `server/src/lib/risk.ts` → `buildSixBoxChecks`

| code | 라벨 | 데이터 근거 | green / yellow / red / gray |
|---|---|---|---|
| `eligibility` | 공고 요건 | program_requirement 규칙 평가 | 미등록 gray / 충족 green / 재검토 red / 추가확인 yellow |
| `survival` | 생존 위험 | 휴폐업, 매출·고용 백분위, 업력 | AUC 채택 축 위주 |
| `capacity` | 사업수행 기반 | 인력, 연구소/전담부서/연구원, 자본 여력 | 2요소 충족=충분, 자본소진 시 강제 보완 |
| `post_support` | 지원 후 관찰 | observed_changes_after_support | 변화 관찰/일부/미확인/산출불가/이력없음 |
| `support_focus` | 지원 집중 | awarded, 중첩, 동일목적, 연속수혜 | 이력없음 gray, 중첩·반복 yellow |
| `data_quality` | 데이터 신뢰도 | 매출·자본·고용·설립일 결측 | 결측 0/1/2+ |
| `finance` | 재무 신호 | 자본소진, 부채, 영업이익률, 매출급감(≤−30%) | **참고 축** (생존 점수 아님) |
| `revenue_scale` | 매출 규모 | 테스트·레거시 호환용 보조 칸 | 화면 6칸에서 제외 가능 |

**의도적으로 화면에 안 뿌리는 것**

- “선정 추천이 아니라…” 같은 설계 설명
- “데이터로 확정 불가 항목 있음” 같은 구현 메타 문구  
→ 담당자 언어로만: `공고 미등록`, `추가 확인`, `요건 재검토`

신호별로 **자료 요청 질문**만 생성:

- 자본 소진 → 차입 명세·상환일정·자본총계 변동
- 중첩 → 협약서 목적·인력·비용항목 대조
- 동일 목적 반복 → 직전 산출물 vs 이번 단계 차이
- 금액 0원/미상 → 비금전/미입력 확인

## 7. 생존/참고 지표 배열

### 7.1 survival_indicators

| code | AUC | weight | 주의 조건 |
|---|---:|---:|---|
| revenue_level | 0.704 | 1 | pctl < 30 |
| tenure_years | 0.671 | 1 | < 3년 |
| employment_level | 0.609 | 1 | <2명 또는 pctl < 30 |
| revenue_growth | 0.475 | **0** | <0 caution (호환용으로 survival 배열에 남김, 점수용 아님) |

### 7.2 reference_indicators

| code | AUC | weight | 주의 조건 |
|---|---:|---:|---|
| debt_ratio | ~0.50 | 0 | >100 caution, >200 또는 자본소진 warning |
| operating_margin | 0.558 | 0 | <0 caution |
| rd_intensity | — | 0 | missing 가능 |

프론트 재무 탭:

- 생존 표: AUC 컬럼 + 근거(ⓘ)
- 참고 카드: 회색 점선 영역, “참고지표”

### 7.3 evidence (근거 패널)

`makeEvidence`가 지표별 메타 연결:

| code | 필드 라벨 | 산식 문구 |
|---|---|---|
| revenue_level | 매출액 | 천원 → 백만원 환산 |
| tenure_years | 설립일자 | 기준연도 − 설립연도 |
| employment_level | 국민연금 가입자수 | (원천) |
| revenue_growth | 매출액 | (당해−전년)/전년×100 |
| debt_ratio | 부채총계/자본총계 | 부채÷자본×100 |
| operating_margin | 영업이익/매출액 | … |
| rd_intensity | 연구개발비/매출액 | … |

프론트: 지표 옆 Info 아이콘 → 하단 고정 패널 (원천 파일·시트·필드·기준연도·값·산식).

## 8. as_of (시점 절단) 규칙

지원 심사 시 **선정일 이후 재무를 쓰면 안 된다.**

```text
fiscalYearAvailableAt(date):
  월 ≤ 4  → year-2
  월 > 4  → year-1

cutoffFy = resolveAsOfFy(yearlies, round.as_of_fy, as_of_date)
yearlies  = fiscal_year ≤ cutoffFy 만 사용
support   = selected_date ≤ cutoff 또는 source_year 폴백
NTIS      = base_year ≤ cutoff (미상 연도는 집계 제외 + 경고)
```

과거 회차 조회 시 `data_warnings`에 “회차 기준시점 이후 제외” 문구.

## 10. 검증 케이스 (분석이 코드에 남는지)

### 10.1 기업 2124 — 재무 리스크 + 부분 중복수혜

| 관찰 | 코드 출력 |
|---|---|
| 2024 매출 11.1억, 영업이익률 −82.3% | finance red, brief에 명시 |
| 자본 3.5백만원, 부채비율 산출 98,077% | “자본 소진 임박 …” |
| 원장 5건 중 지원대상 3 / 탈락 2 | awarded=3, rejected=2 |
| 인력양성 목적 2회 | same_purpose_repeats |
| 수행기간 중첩 1쌍 | overlap_pairs length 1 |
| 확인 지원금 36백만원 (6.4+9.6+20) | awarded_amount_million=36 |
| 매출 규모 동종 61백분위, 고용 85백분위 | survival green (규모 축은 양호) |
| 매출 성장 −73% | revenue_growth caution + finance note |

**해석:** 생존 “규모 축”은 괜찮지만 **재무 완충력·중복수혜 대조**가 본 게임.  
담당자 질문: 상환여력, 자부담, 직전 지원 산출물.

### 10.2 기업 1549 — 중복수혜 heavy

| 관찰 | 코드 출력 |
|---|---|
| 지원대상 다수 (최근 3년 21건 수준) | support_focus yellow |
| 기간 중첩 54쌍 | badges “중첩 있음” |
| 시제품 목적 6회 등 | same_purpose_repeats |
| 부채비율 246%, 매출 −31.7% | finance yellow |

**해석:** 재무보다 **예산 중복·동일 목적 반복 점검**이 핵심.

### 10.3 기업 146 — 비교적 양호 대조군

- 부채비율 낮음, 지원 소수 → 점검 칸이 green 위주.
- “깨끗한 기업”을 추천하는 게 아니라, **신호가 적음**을 보여 줌.

## 12. 하지 않은 것 / 한계 (분석 정직성)

1. **자동 선정·탈락 점수 없음** — 정책상 금지.
2. **지원 인과효과 추정 없음** — p=0.086 유의 미달, 개별 화면 비표시.
3. **CRETOP 신용·EW 미연동** — 슬롯만 설계, 데이터 없음.
4. **사업자번호 없음** — 가명키 `기업_{id}` 만 사용.
5. **사상구 통계** — 기초지자체가 사상구일 때만 regional_context 적용.
6. **주요제품 “홈페이지” 등** — 제품 설명으로 보기 어려운 원천값은 화면 제외 + warning.
7. **부채비율 극단값** — 산식 유지 + 해석 레이어 (원천 오류 수정이 아님).

## 14. 변경이 분석에서 코드로 흘러간 경로 요약

```text
OT 페인포인트
  → v3.3 통계 검증 (AUC, 2×2, 중복수혜 정의)
    → 리포트 양식 (6칸, 금지 문구, episode/component)
      → ETL 파생지표·백분위·SQLite
        → risk.ts 규칙 엔진 (채택 지표 vs 참고, 지원대상 필터, 자본소진 해석)
          → report-engine 조립 + evidence
            → api mapCompanyReport
              → company-report UI (요약/재무/중복/비교/모의지원)
```

**분석의 역할은 “똑똑한 문장 생성”이 아니라,  
어떤 필드를 어떤 단위·어떤 비교집단·어떤 임계값으로 보여줄지 고정하는 것**이다.  
그 고정값이 지금 코드의 `threshold.json`, `INDICATOR_META`, `buildSupportSummary`, `interpretDebtRatio`, `mapCompanyReport` 에 들어가 있다.
